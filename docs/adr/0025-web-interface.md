# ADR-0025: Web interface: complete application, Qute and htmx, `orpheus serve`

**Status**: proposed, 2026-10-04 (design in progress with the user; implementation after the English
migration, ADR-0022). Supersedes ADR-013.

## Context

The Python web UI was removed with `44146f0`, and the Java `orpheus-web` module, left empty, on
2026-09-27. ADR-013 had fixed a separate SPA on REST in the same artifact, to be revisited when work on
the interface resumed. In the meantime Node was removed from the repository (Markdown lint moved to
rumdl, 2026-09-27).

## Decisions taken (2026-10-04)

1. **Scope: complete application.** Review queue with the actions per category, history of the ledger
   entries of every track with search and filters (SPEC.md section 5), starting and following imports,
   configuration, browsing and listening to the library.
2. **Process: an `orpheus serve` subcommand.** It starts the server until it is closed; `orpheus import`
   stays a command of its own. Same artifact, same database. The `serve` process also runs the imports
   started from the GUI, in the background; a lock in the data folder prevents two simultaneous imports
   on the same database, from the CLI or from the GUI.
3. **Frontend: pages generated by the server with Qute, interactivity with htmx.** No Node, no
   JavaScript build; a few pages for a single user. Replaces the REST SPA of ADR-013.
4. **Access: localhost only.** The server listens on 127.0.0.1, a single user, no authentication.
5. **Development priority**: review queue with actions and history; browsing and listening to the
   library; imports from the GUI with progress; configuration.
6. **Language**: texts in Qute message bundles, English by default, Italian as a second language.
7. **Listening in the browser** (files served by the server to the `<audio>` element): simple playback,
   A/B comparison between two versions (copy and original, alternative versions, duplicates), jumping
   to the reported points (SIT tones, dropouts, start of a truncation), a waveform generated by the
   server with ffmpeg as an image.
8. **Review queue actions** (core functionality, exposed by the GUI). Every action moves or retags the
   copy in the library and writes a ledger entry:
   - Tier 2 reconstruction: accept; undo (the track goes back to where it would have been without Tier
     2: the tags' album or Unidentified); choose another release among the candidate releases;
   - unidentified: search MusicBrainz by artist and title and choose the release; accept as is;
   - Tier 3 suggestion: use it for the MusicBrainz search; reject it;
   - tag correction: accept; restore the original of all fields or of a single one (from the
     `ORPHEUS_ORIGINAL_*` tags);
   - damaged file: mark as known (replacement comes with the guided replacement, SPEC.md section 6);
   - identical duplicate: keep both; remove the copy from the library;
   - alternative version: keep; make it the main one (swap of names); remove it.
9. **No archive**: a file removed from the library is deleted from the library; the file stays in the
   source, which is never touched. If an in-place import is ever done (item in `docs/TODO.md`), this
   choice must be revisited: the source would no longer be a safety copy.
10. **Persistent decisions**: the decisions taken in review are saved in the database tied to the source
    file (path and audio hash) and applied again at every later import.

## Alternatives considered

- **Narrower scope** (review and history only, or with imports): discarded by the user.
- **Server only, CLI as a client**; **two separate artifacts**: discarded in favour of `serve`.
- **SPA with Quarkus Web Bundler** (esbuild via Maven, without Node installed) and **classic SPA with
  Node**: discarded in favour of Qute and htmx.
- **Access from the local network** with authentication: discarded.
- **Archive of removed files** in the data folder or in a folder of the library: discarded.
- **Replacing a damaged file** from the review queue: postponed to the guided replacement.
